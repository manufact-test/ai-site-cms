# ADR 0013 — Автоматически безопасные блоки и принцип проверенного повторного использования

**Согласовано:** 19.10.2026. **Реализация:** ещё не начата как продуктовая функция; в Stage2 есть лишь пустой лабораторный каркас. Подробный стандарт: [SITE-QUALITY-BASELINE.md](../SITE-QUALITY-BASELINE.md).

## Суть решения

Когда MANUFACT просит ИИ «сделай сайт по прототипу», «без макета» или перечисляет секции, ИИ **без дополнительных напоминаний** создаёт оригинальный дизайн, адаптив, рабочие сценарии и schema/manifest для всех используемых блоков. Если есть форма, её защита от ботов, серверная валидация, проверка международных телефонов, обработчик и честная обратная связь не должны появляться лишь после отдельной просьбы. То же относится к кнопкам, FAQ, меню, popups, медиа и общим базовым требованиям.

Важно различать «CMS позволяет редактировать антиспам/валидацию» (предусмотрено изначальным №76–83) и «ИИ автоматически подключил проверенный механизм при генерации формы» (новое согласованное обязательство).

## Правило разработки: сначала исследовать, потом создавать

1. Искать **поддерживаемое, проверенное open-source решение или опубликованный стандарт**, прежде чем реализовывать любой базовый механизм самостоятельно. Сравнить текущие версии, актуальность, security record, лицензию/NOTICE, вес и поведение, совместимость PHP8.1+, Apache/Nginx, HTML/PHP/React/Next, shared hosting без обязательного Node.
2. **Реюз не означает бездумное копирование.** Приоритет лицензиям MIT/BSD/Apache-2.0 с атрибуцией. Не включать GPL/AGPL или платные ограничения без отдельного согласования. Фиксировать источники, версии, lock/sha, поддерживать регрессионные тесты. Готовые UX-принципы не требуют импортировать весь фреймворк.
3. **Кандидаты к аудиту, НЕ принятые зависимости:** OWASP ASVS/Cheat Sheets — правила security; WCAG/WAI-ARIA, GOV.UK Design System — UX/accessibility; libphonenumber и PHP-совместимые лёгкие варианты — телефоны; Radix UI — возможный React-specific UI. Это разные типы источников, не одна универсальная библиотека и не автоматические рекомендации к установке.
4. После проверки оформить единые протестированные **модули и контракты**, повторно используемые во всех будущих сайтах и вариантах рендеринга; не тащить React на PHP-сайт. Включать только функциональность, реально применимую к данному блоку; не создавать ненужные поля редактора.
5. Автоматическая приёмка по [baseline](../SITE-QUALITY-BASELINE.md): PASS / FAIL / N/A с причиной / CONFIGURATION_REQUIRED; нельзя объявлять форму полностью рабочей без настроенного получателя, реальной доставки и безопасной серверной обработки.

## Фазы

**Stage2:** фиксация политики и кандидатов; никаких преждевременных Stage3 функций. **Stage3:** контракт AI↔Site↔CMS, типы блоков/manifest/coverage. **Stage4, 8, 11:** общие библиотеки, формы, интерактивы, безопасность. **Stage5–10, 13:** визуальные и платформенные адаптеры. **Stage14–16:** end-to-end verification и release. Приёмка 135/135 остаётся обязательной; первоначальные 193 ответа и 18 этапов не меняются.
