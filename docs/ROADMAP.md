## 1. Что разрабатываем

AI Site CMS — независимый редактор **готовых сайтов, создаваемых ИИ по явному техническому контракту**. ИИ разрабатывает страницу и одновременно регистрирует её компоненты, стабильные ID, редактируемые свойства, исходные значения, варианты адаптива, правила поведения и тесты. CMS обеспечивает ручные правки без редактирования кода.

- Не визуальный конструктор страниц, не замена Elementor/Tilda для сборки новых страниц вручную.
- В редакторе загружена **одна выбранная секция**, слева предпросмотр, справа параметры, дерево/клик для выбора элемента.
- Отображаются только свойства, действительно используемые на конкретном сайте/в выбранном блоке; новые свойства при генерации ИИ регистрируются через контракт автоматически.
- Любые ручные изменения сохраняются при обновлениях кода, возможные конфликты проверяются и разрешаются до публикации.
- Даже при заказе «сделай сайт на свой вкус» ИИ готовит полную машиночитаемую схему администрирования (№119).
- Сайты имеют раздельные инсталляции и данные. Сайт продолжает работать при недоступной CMS.
- **Не трогать CELIKOM**: он создаётся независимо в другом репозитории. Пробное подключение — только после полного релиза AI Site CMS и отдельного согласования.

Основной источник истины: [MASTER-TZ.md](MASTER-TZ.md) и [REQUIREMENTS.md](REQUIREMENTS.md); приоритеты также хранятся в ../requirements/requirements.csv и Excel-реестре. Этот план не меняет их.

### Этап 2. Адаптация выбранной основы и финальная архитектура

**Задачи:** выбрать архитектуру ядра и редактора; принять ADR по runtime, БД, API и состояниям; определить границы пакетов CMS/сайт/адаптеров/SDK; определить правила владения данными, миграций, и инфраструктуру тестирования. Если подходит чужой код — **законно подключить зависимость или сделать fork по лицензии**, сохранить атрибуцию и историю источника; удалить/не включать функции конструктора, которые нам не нужны. Если тяжёлая CMS не подходит — взять лишь точечные библиотеки либо написать собственную компактную основу.

**Особый критерий:** **не** обещать полноценный Next.js SSR на PHP-only хостинге: Next static export может жить на обычном хостинге, SSR требует соответствующей серверной среды. При этом движок CMS обязан уметь жить на обычном shared hosting.

**Артефакты:** docs/ARCHITECTURE.md после принятия решений, docs/ADR/* (создать по мере решений), дерево исходного кода, лицензии/NOTICE, инструкции разработки и воспроизводимая тестовая сборка.

**Приёмка:** архитектура согласована, зависимости легальны и фиксированы, образец пустой CMS запускается в целевой среде; нет преждевременной реализации страниц клиента.

### Этап 3. Контракт ИИ — главная отличительная функция

**Задачи:** стандартный контракт разработки AI-сайта; манифест каждого блока (ID элемента, дерево, типизированные свойства, редакторы, defaults, используемость, адаптив, связанные ресурсы), регистрация нестандартных компонентов; автоматическое формирование UI; проверки полноты и корректности; изменения схемы при обновлении; стабильные IDs; предотвращение silent overwrite.

**Обязательно проверить:** сценарий без какого-либо дизайн-ТЗ — ИИ генерирует сайт «на своё усмотрение» и сразу полноценную схему управления; отсутствующие свойства не появляются в панели. Никакая ИИ-модель не должна быть жёстко зашита в CMS.

**Артефакты:** версионированный docs/AI-SITE-CONTRACT.md, JSON-schema/SDK (после старта кода), генератор/валидатор, фикстуры корректных и некорректных блоков.

**Приёмка:** сценарии №101–119 проходят автоматически, в том числе обновление компонента с новыми свойствами и проверка на потерю ручных настроек.

**Приёмка:** критические и блокирующие проблемы закрыты; готовность к формальной полной приёмке подтверждена.

### Этап 15. Формальная приёмка обязательного объёма

**Задачи:** по каждому из **135 обязательных ID** сохранить ссылку на реализацию, автоматический или ручной тест, результат, исправления и отметку владельца. Проверить границы «Желательно / Не нужно», лицензии, установку с нуля, обновление, полный rollback.

**Артефакты:** матрица 135/135 и подписанный владельцем отчёт, docs/ACCEPTANCE.md с фактическими результатами.

**Приёмка:** **135/135 подтверждено**, нет незакрытых критических дефектов и потерь пользовательских данных. Пока этого нет — нет первого полноценного релиза.

### Этап 16. Первый полный релиз

**Задачи:** зафиксировать версию, релизный пакет, список изменений, документацию инсталляции на shared hosting, инструкции по безопасности, AI-контракт, руководство по backup/update/rollback, контроль целостности сборки.

**Приёмка:** владелец принимает **полностью готовую CMS**; только после этого допускается переход к интеграции существующих сайтов.

### Этап 17. Отдельное безопасное испытание на CELIKOM, затем другие сайты — после полного релиза

**Цель:** использовать **CELIKOM только как первый независимый испытательный сайт** для полностью готовой AI Site CMS. **Не объединять проекты**: CMS и CELIKOM сохраняют собственные репозитории, исходный код, базы данных, учётные записи, CI, деплой, документацию и продуктовые дорожные карты. CELIKOM — полигон проверки готового продукта, **не** новая часть CMS и не общая платформа разработки.

**Задачи:** после завершения этапа 16 и отдельного разрешения владельца подготовить точечный план пилота; изучить совместимость с текущим сайтом CELIKOM; сделать полные резервные копии и план восстановления; развернуть **изолированную тестовую копию CELIKOM**; подключить CMS через согласованный адаптер без смешивания репозиториев/данных; пройти тесты редактирования, публикации, сохранения пользовательских правок, обновления, безопасности и возврата предыдущего состояния. **Никаких действий на рабочем сайте CELIKOM до отдельного подтверждения.**

**После CELIKOM:** при подтверждённой успешной работе и по следующему решению владельца перейти к проверкам на других независимых сайтах.

**Граница:** это безопасное разовое испытание и миграция конкретного тестового сайта после полного релиза, **не** универсальная функция импорта чужих сайтов (№180 — «Не нужно») и не часть разработки CELIKOM.

**Приёмка:** CELIKOM как независимый пилот работает без регрессий; исходный проект не сломан, данные не объединены, протестированы резервирование и откат; владелец подтвердил результат. Затем допускаются другие сайты.

## 4. Правила ведения разработки

1. **Одна стадия — один явно проверяемый итог.** Закрытие только после проверки и подтверждения владельцем. Не закрывать этап по наличию кода без работающих тестов.
2. **Исходные приоритеты неприкосновенны.** Любое изменение требования/категории только по отдельному решению владельца с обновлением реестра.
3. **Документация движется вместе с кодом.** По завершении стадии синхронизировать MASTER-TZ, ROADMAP, ARCHITECTURE, AI-SITE-CONTRACT, OPEN-QUESTIONS, ACCEPTANCE, PROJECT-STATUS.json, NEXT-CHAT, если затронуты.
4. **Каждый этап:** план → согласование рисков → реализация → тесты → замечания владельца → исправления → приёмка → чекпоинт.
5. **Не копировать чужой код без прав.** Лицензии, зависимости и происхождение сохранять; не делать fork только потому, что редактор выглядит похожим.
6. **Желательные не блокируют первый релиз**, если отдельно не повышены по приоритету. Реализованные желательные проходят тестирование наравне с обязательными.
7. **Готовые исходники сайта CELIKOM недоступны для записи из этого проекта.** Никаких общих БД, секретов, деплоев, CI или принудительного слияния репозиториев.
8. **Прозрачность:** реальный статус проверять по GitHub и тестам, не по словам в прошлом чате. Не выдумывать завершённые стадии.
9. **Перед сменой чата** обновлять docs/NEXT-CHAT.md и PROJECT-STATUS.json; сохранять ссылку на последний commit/issue и ближайший конкретный шаг.
10. **Никаких вымышленных дат.** Оценка сроков после технического исследования и утверждения реальной архитектуры.
