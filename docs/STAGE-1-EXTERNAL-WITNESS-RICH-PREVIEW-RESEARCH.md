## Research block A: independent receipt against whole SITE volume rollback

File: research/stage1/external-trust-witness.cjs. Relies on the real PHP 8 CLI signed extension / HMAC file trust implementation from v1.25. Signed receipt uses separate **ephemeral Ed25519 witness key**, explicit service identity, local state generation/version/digest/revocation/owner hash/state hash, and a previous-receipt hash, held in a distinct test directory outside the simulated attacker-controlled site volume. The private witness signer is held by the test runner, NOT the site PHP file.

**42 assertions, 10 refused cases, 24 fresh PHP process invocations** in the separate witness runner, all PASS on GitHub Actions. Site-only **joint rollback of state.json and anchor.json**, which v1.25 proved invisible to local HMAC, becomes detectable when the separately signed latest witness record is trusted and non-replayable. Local commit before remote witness confirmation fails closed; signed forged or tampered receipts and missing current receipt are rejected. Privileged witness checkout refuses older-generation candidates, so merely asking the witness to sign a stale restored site cannot bypass a retained latest receipt. Revocation reflected in retained external record blocks site volume restore.

**Crucial negative result:** restoring **BOTH the site and the external witness receipt** to a mutually consistent old copy again BYPASSES detection. Even Ed25519 integrity, signed previous-hash data and two directories are NOT a real immutable external monotonic counter. A test-only protected witness writer is NOT a deployed remote attestation service. Production still requires verified independent append-only/monotonic retention with separately authenticated issuer approval, durable/fenced concurrent writes, key custody and rotation, recovery/backup protocol, meaningful network isolation and an auditable host/provider choice. Evidence is bounded to simulated trust boundaries on a GitHub runner; never claim signed files themselves are immutable. No external provider, Hostinger, actual internet API or production plug-in permission model was used.

## Research block B: real Chromium original mixed-site appearance in a restricted preview

Files: research/stage1/cedar-rich-browser-boundary.cjs and fixture research/stage1/fixtures/cedar-lab-standalone.html (added pulse class to activate existing CSS keyframes). Uses pinned playwright-core 1.55.1 against installed system Google Chrome/Chromium on GitHub Actions; prior researchers' original standalone site was unannotated and researcher-authored, NOT blindly generated by an independent LLM.

**23 successful browser assertions**: structural DOM and element IDs, visual computed gradient, SEO title/description/canonical, picture srcset/alt, video source, CSS desktop 3-column grid, 390px mobile 1-column grid with H1 36px, animation working at normal preference, animation disabled by prefers-reduced-motion:reduce, CSS/source parity across original and CSP-restricted opaque sandbox at desktop/mobile/reduced-motion. Native HTML details/summary toggling works in both.

**Security-vs-fidelity tradeoff proven:** original baseline inline JavaScript can change menu aria-expanded. In restricted srcdoc with sandbox and restrictive nonce-free script-src 'none', untrusted inline JS is NOT executed; the same menu interaction is therefore intentionally lost (it is not equivalent to full-site runtime parity). Restricted native FAQ still works; preview's untrusted form does not initiate a network request, with research route intercepting any attempted external requests. Merely retaining original HTML/CSS and metadata inside a sandbox is a visually useful read-only fidelity experiment, **NOT safe CMS editability, trusted form submission, real production hosting or JS feature equivalence**. No isolated iframe security claim beyond these checks.
