# Стандарт готовности AI-сгенерированных сайтов и блоков

**Утверждено владельцем:** 19.10.2026. **Это план/контракт, не реализованный код.** См. [ADR 0013](ADR/0013-ai-site-safe-defaults-and-reuse.md), [контракт ИИ↔сайт](AI-SITE-CONTRACT.md). Стандарт действует для сайтов без макета, по прототипу и по подробному ТЗ.

## Общие правила

- Созданная страница должна содержать не только внешний вид и type-safe редактируемые свойства, но и **все применимые по функциям проверенные механизмы поведения, защиты, адаптива и доступности**. Не нужно каждый раз спрашивать владельца, нужна ли антиспам-защита формы.
- Проверять **каждый используемый тип блока**: PASS / FAIL / N/A (с причиной) / CONFIGURATION_REQUIRED (не хватает секретов/получателя/правовых или инфраструктурных настроек). Не путать визуально красивый mock с рабочей поставкой. FAIL и CONFIGURATION_REQUIRED блокируют утверждение «готово».
- Не грузить лишний runtime и не показывать в админке свойства, которые конкретный блок не использует. Готовые безопасные дефолты должны оставаться редактируемыми по исходному manifest-контракту, если это допустимо без ослабления защиты.
- Обработка посетительских запросов, включая формы, должна быть независима от uptime админки и центрального сервера MANUFACT. Нужные обработчики настраиваются в архитектуре конкретного сайта/совместимой службы.

## Матрица стандартов по блокам

| Блок/сценарий | Готовность по умолчанию | Как проверять |
|---|---|---|
| Формы, в том числе многошаговые | Клиентская UX- и ОБЯЗАТЕЛЬНАЯ серверная валидация, обязательные/необязательные поля, лимиты по типам/размеру; international phone parser по стране (не 9/10-значная regex), email; honeypot, разумный rate limit, защита от повторного submit/дублей, защита от ботов, CSRF/origin модель по контексту, HTTPS/secret isolation, безопасное кодирование вывода и errors | invalid/spam/replay отвергнуты; нормальные международные номера приняты; доступность ошибок с клавиатуры; 1 submit = 1 заявка |
| Обработчики email/Telegram/CRM | Настроенный получатель и настоящая серверная доставка, неутекающие ключи, retry/queue там, где нужно, без дублей; человек видит фактический результат, а не фиктивное «отправлено» | Реальная тестовая доставка; отсутствие адресата/секрета = CONFIGURATION_REQUIRED; сбой API не подменяется успехом |
| Кнопки, ссылки, CTA | Валидные действия, URI/якоря/формы, отсутствие сломанных ссылок и ложных кнопок; hover/focus/active/disabled/loading по необходимости, keyboard/touch | Кнопки реально работают на ПК/планшете/телефоне; безопасные targets |
| FAQ, accordion, tabs | Корректные состояния/ARIA, keyboard, управление фокусом, reduced motion, плавное открытие и закрытие без двухступенчатых скачков | Открыть/закрыть; ESC если применимо; нет изменения высоты после завершения анимации |
| Header/меню/модалки/popups | Mobile UX и safe-area, keyboard, ESC, scroll lock по контексту, focus trap и return-to-trigger для modal, доступное закрытие | Нет застрявшего фокуса, горизонтального скролла, перекрытия содержимого |
| Изображения/видео/галереи/анимация | Валидные ресурсы, alt/decorative, размеры, оптимизация, адаптив; lazy-loading кроме важных LCP-ресурсов; captions/controls при необходимости, prefers-reduced-motion | Нет broken assets/layout shift, ненужного тяжёлого фонового медиа, исключений без объяснения |
| Любой блок и страница | Responsive desktop/tablet/mobile, контраст/семантика/клавиатура, security XSS/CSRF по контексту, адекватные ошибки, SEO и доступность, отсутствие горизонтального скролла | Функциональный, a11y, security, performance и визуальный smoke на применимых site families |

## Базовая безопасность форм

1. Защита **многоуровневая**: backend validation, abuse throttling, honeypot и при необходимости challenge/CAPTCHA; CAPTCHA не навязывать всем автоматически (privacy/дополнительная зависимость/доступность). Не полагаться лишь на HTML required или JS.
2. Номер телефона проверять по стране и международным префиксам; выбирать подходящий PHP/JS adapter после оценки upstream. Не блокировать реальные номера простой жёсткой регуляркой.
3. Без реального получателя/endpoint/API-ключей форма не выдаёт фальшивое подтверждение. Секреты не публикуются в JS/config; ошибки и журналы не раскрывают токены или лишние персональные данные.
4. Ограничить тело запроса, тип/размер файлов, защитить загрузки, URL и вывод; продумать CSRF/origin для публичных анонимных форм и rate limit на IP/учётную запись с учётом proxy.
5. Проверить применимые требования к privacy/согласию/retention и каналы доставки на реальном проекте, не добавлять декоративное согласие без правовой цели.
6. В многошаговых формах повторно валидировать итоговый payload, обеспечивать управление клавиатурой и сохранение корректного введённого в рамках формы.

## Перед созданием модуля — приоритет готовых решений

Сначала shortlist и security/license/maintenance/runtime-review; затем proof-of-compatibility, pin/versioned adapter, единые тесты и реюз. Оценить OWASP/ASVS, WCAG/WAI-ARIA, GOV.UK patterns, libphonenumber variants, Radix для React. **Это кандидаты, а не уже принятые/установленные зависимости.** Собственная реализация разрешена, если сторонняя не подходит по безопасности, качеству, лицензии, платформе или размеру.

## Приёмочные тесты до первого релиза

- В сценарии без макета ИИ генерирует **форму с реально работающим валидируемым обработчиком, антиспамом, тестовой доставкой**; если интеграция не настроена, честно выводит CONFIGURATION_REQUIRED.
- Тесты бот/флуд/invalid phone, повторная отправка, доставка, сбой связи/тайм-аут, XSS, CSRF/origin, a11y, responsive; negative cases не позволяют сообщить о несуществующей отправке.
- Проверить компоненты на HTML/PHP/React/Next в поддерживаемых режимах с учётом реальной инфраструктуры; CMS/editor можно остановить, не ломая публичный сайт и обработку посетительских заявок.
- Проверить лицензии и актуальность выбранных зависимостей в момент реализации, а не на основании названий библиотек в ТЗ.
