# Исследование потенциальных open-source основ — предварительно

**Ничего пока не выбрано.** Выбирать библиотеку только после закрытия `OPEN-QUESTIONS.md` и испытаний под наш сценарий «ИИ делает сайт, CMS редактирует только зарегистрированные свойства».

| Кандидат | GitHub | Основная идея | Предварительная оценка |
|---|---|---|---|
| GrapesJS | https://github.com/GrapesJS/grapesjs | Визуальное редактирование HTML-компонентов | Многие механизмы редактирования готовые, но ручной конструктор нам не нужен; проверить накладные расходы и встраивание |
| VvvebJs | https://github.com/givanz/VvvebJs | Редактор HTML-блоков и компонентов | Возможна удобная интеграция с PHP; может содержать лишнюю для нас функциональность |
| Puck | https://github.com/puckeditor/puck | Редактор React-компонентов | Удобно для React, но универсальная поддержка PHP и статических сайтов потребует адаптеров |
| Craft.js | https://github.com/prevwong/craft.js | База для React-редактора | Высокая гибкость, но больше UI придётся строить самостоятельно |
| Vvveb CMS | https://github.com/givanz/Vvveb | Полноценная PHP CMS | Риск ненужной общей функциональности и лицензионных обязательств |
| Microweber | https://github.com/microweber/microweber | Готовая PHP CMS | Много готовой инфраструктуры, но другая продуктовая модель |
| Payload | https://github.com/payloadcms/payload | TypeScript/headless CMS | Сильная модель контента, но другой runtime и инфраструктурные ограничения |

Возможно, лучшей основой окажется **не** одна крупная CMS, а небольшие библиотеки: панель настроек, типизированные формы, iframe preview, схемы/валидация, content store и revision engine.

## Как выбирать

Проверить отдельно: лицензия и возможность коммерческого использования; поддержка переиспользуемого `manifest`; размер/зависимости; запуск на общем PHP-hosting; React/Next адаптер; работа одного блока в изоляции; сохранение overrides; безопасность; качество сопровождения. Для GPL/AGPL обязателен отдельный анализ обязательств по распространению и модификациям; не включать такие проекты автоматически.

Не делать fork до архитектурного решения. После тестов составить таблицу соответствия **каждому из 135** обязательных пунктов: «из коробки / потребуется адаптер / придётся разработать».
