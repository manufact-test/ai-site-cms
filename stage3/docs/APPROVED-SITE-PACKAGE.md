# External approved website: folder handoff

**Purpose:** Connect an externally developed **finished site**, built only after client approval of three static prototype images. This is neither a PNG-to-code converter nor evidence that the client really approved; the operator must confirm approval. The design/specification files stay in the portable folder for future AI update work, not in the CMS database.

```text
approved-site/
  handoff.json
  site.json
  prototypes/desktop.png
  prototypes/tablet.png
  prototypes/mobile.png
  client-explanation.md
  implementation-spec.md
  assets/asset-hero.jpg
  assets/asset-hero-mobile.jpg  # optional responsive image variant
```

```json
{
  "format": "manufact-approved-site-handoff-v1",
  "status": "approved",
  "version": "client-approved-v1",
  "files": {
    "site": "site.json",
    "desktop": "prototypes/desktop.png",
    "tablet": "prototypes/tablet.png",
    "mobile": "prototypes/mobile.png",
    "clientExplanation": "client-explanation.md",
    "implementationSpec": "implementation-spec.md"
  }
}
```

The `site.json` is the actual completed site contract (`manufact-ai-site-v1`) using **already registered** CMS component manifests. Images referenced in `site.assets` must exist in folder paths corresponding to the canonical `/assets/...` URL; responsive variants have the same requirement. The code/renderer is not generated by this import. No executable third-party HTML, JS, external URLs or new component definitions are imported.

In authenticated server Studio, the owner chooses **Подключить готовый сайт**, picks the folder in a Chromium-compatible directory picker, and confirms the real client approval. The existing typed validator checks the actual site JSON. The existing authenticated API first creates a nonpublished seed (because createSite forbids unstored images), stores each real image into this site's isolated database, issues new immutable IDs, and Save replaces the seed with the fully mapped site manifest. Current page/FAQ/SEO/image editing, Publish and rollback work via the existing CMS path. No network requests to AI providers; no publication without separate user action.

Limitations of this first vertical handoff: images are PNG/JPEG/WebP up to 450 KB per source and variant, at most three supported responsive variants, site.json <=500 KB, prototype image <=8 MB; SVG and MP4 need separate current Studio flows. Client explanation and portable specification are required to be present but qualitative review is human. Errors stop import; after remote creation a recoverable *unpublished* partial seed may remain, never a half-published site. Preserve the original local folder; currently CMS does not archive the client prototype files. Unsupported custom HTML components are a future contract integration task, not automatically 'converted'.

## Individual AI-authored sections (no fixed templates)

**Contract support:** The registered `custom-section@1.0.0` component allows an external AI to deliver an original visual composition in `section.designGraph`, without claiming that one of the fixed demo blocks reproduces its design. The section must contain exactly one `section-note` element with `values: {"content.text":"<internal note>"}`; this field is internal metadata, not the published title. The actual page is rendered from the typed graph and edited through Studio's Design Graph controls. `designGraph` is mandatory for this component in both browser and server validators, so empty or half-built custom sections cannot be saved/published.

The existing Design Graph vocabulary supports containers, headings, text, safe links/buttons, images, icons, separators and controlled video, with independent responsive rules, hover/focus styles and allowlisted motion. The external AI must write these nodes, their responsive styles, actual media IDs and interactions into `site.json`. This is an **individual design**, not unrestricted HTML/CSS/JavaScript import. A client-approved design that needs a behavior beyond the current controlled vocabulary must be explicitly implemented and reviewed as a versioned first-party CMS capability before import. The three static prototype images and full descriptions remain mandatory.

Example section (append to a page's `sections` array; replace the graph nodes with the actual approved design):

```json
{
  "id": "section-custom-brand",
  "component": "custom-section",
  "manifestVersion": "1.0.0",
  "elements": [
    {
      "id": "element-custom-brand-note",
      "slot": "section-note",
      "values": {
        "content.text": "Авторский первый экран"
      }
    }
  ],
  "designGraph": {
    "version": 1,
    "id": "graph-custom-brand",
    "nodes": [
      {
        "id": "brand-layout",
        "type": "container",
        "styles": {
          "display": "grid",
          "columns": 2,
          "gap": 24,
          "padding": 32
        },
        "responsive": {
          "tablet": {
            "columns": 1
          },
          "mobile": {
            "padding": 16,
            "gap": 12
          }
        },
        "children": [
          {
            "id": "brand-heading",
            "type": "heading",
            "level": 1,
            "text": "Ваш согласованный заголовок",
            "styles": {
              "fontSize": 52
            },
            "responsive": {
              "mobile": {
                "fontSize": 32
              }
            }
          },
          {
            "id": "brand-intro",
            "type": "text",
            "text": "Согласованное описание услуги",
            "styles": {
              "fontSize": 18
            }
          }
        ]
      }
    ]
  }
}
```

Use a graph heading with level 1 only once per page. Validate the entire document before connection; custom-section must include at least one graph node and obey the existing global node, depth and media limits.

## Preflight for a complete external AI handoff

Before opening Studio, run from repository root:

```sh
node stage3/bin/verify-approved-site.cjs /absolute/path/to/approved-site
```

The command validates all existing registered manifests including `custom-section`, graph IDs and allowed styles, cross-section asset references, required three prototype files, descriptions, image MIME/size and responsive variant SHA256. It performs **no writes, network calls, automatic approval or publication**. An affirmative report means structurally compatible, **not** that the actual visual design matches the client's approved prototype. The user still reviews the visuals and explicitly imports/publishes in Studio.

When the owner adds a `custom-section` manually inside Studio, the editor supplies a safe editable starter Design Graph so the UI can open it. This convenience never changes imported `site.json`: direct external site handoffs missing `designGraph` are rejected in browser/PHP. Do not pass the starter graph off as the client's finished design.

## Versioned SHA-256 approval lock (v2)

The earlier `manufact-approved-site-handoff-v1` format remains readable for historical handoffs. For a newly approved client website, seal the finished folder:

```sh
node stage3/bin/seal-approved-site.cjs /absolute/path/to/approved-site client-approved-v1 --confirmed-approved
node stage3/bin/verify-approved-site.cjs /absolute/path/to/approved-site
```

Sealing requires the operator's explicit confirmation of actual client approval. It is **not** proof that a client approved the design. The resulting `manufact-approved-site-handoff-v2` file contains SHA-256 digests for `site.json`, all three prototype images, both text documents, every original image and every responsive variant referenced from the site. Studio verifies the same hashes **before its first server write**. A changed specification, image, mockup or website manifest fails closed. When a client approves a new revision, re-seal deliberately using a new version with `--confirmed-approved --replace`; do not silently edit a sealed package. The integrity lock detects local package modification; it is not a digital signature authenticating the client.

The CLI verifies compatibility with the registered component and Design Graph vocabulary but cannot judge whether final HTML visually matches the three actual mockups. Keep the original versioned handoff separately; the CMS does not store its prototype evidence.

## Mandatory operator review before import

After filesystem, SDK, image and SHA-256 checks, Studio now opens a **visual review dialog** displaying the actual three prototype images, full client-facing explanation, full implementation specification, version, page count and checksum status. The operator can **Cancel** without a database write; **Подключить как черновик** begins the authenticated media import. This UI is not a pixel-diff test and cannot infer that the client approved the prototypes: the operator verifies the three images against external approval records. No HTML from the explanation/specification is executed; it is displayed as plain text. Publishing remains a separate permission-controlled action.

## Offline pilot inventory and human acceptance worksheet

After sealing a real package, generate a **read-only, deterministic Markdown report**:

```sh
node stage3/bin/verify-approved-site.cjs /absolute/path/to/approved-site
node stage3/bin/audit-approved-site.cjs /absolute/path/to/approved-site > pilot-acceptance.md
```

The report includes page URLs and SEO metadata, counts of custom sections, flexible forms and FAQ questions, asset/ALT/orphan warnings, and a **per-page desktop 1280 / tablet 768 / mobile 390 acceptance matrix**. It lists manual checks of FAQ publishing, save/publish separation, delivery, redirects, responsiveness, and rollback. The audit refuses packages that do not pass the existing contract/integrity preflight, but **does not automatically mark any visual or behavioral check as passed**. Save its report next to the manually recorded approval and real screenshots when doing the owner pilot. This is a pilot worksheet, not proof of client approval or visual fidelity.

Studio now additionally presents **the actual typed CMS rendering of every selectable page** at the three widths alongside approved prototype images, using local media bytes as data URLs. The rendered iframes are sandboxed, no scripts/forms execute, and the external site remains unpublished until separately requested. Note that it is the current first-party preview renderer, not the production PHP renderer: repeat visual checks against the actual public HTML after publishing.


## Real public PHP acceptance: full-page desktop/tablet/mobile captures

The pre-import Studio comparison is not the public PHP renderer. For the **actual owner-approved finished customer site**, after its draft has been explicitly published **on an isolated local PHP server**, generate read-only evidence from the actual public URL:

```sh
node stage3/bin/capture-approved-site.cjs /ABS/approved-site \
  http://127.0.0.1:PORT/published/ACTUAL-SITE-ID/ \
  /ABS/pilot-evidence-v1
```

The tool validates the original **sealed v2 handoff** before using the existing installed Chromium driver; it refuses non-loopback URLs, mismatched site IDs, existing output folders and any output inside the sealed package. It captures **all published pages** at 1280, 768 and 390 pixels using full-page screenshots, with JavaScript disabled, all cross-origin requests blocked and motion reduced. Output includes `report.html` (shared three approved prototype images alongside real published screenshots), `evidence.json` (hashes, viewport sizes, URL and missing-image warnings), and PNG screenshots. It does **not** modify the CMS database, publish, deploy, send requests to third-party origins or prove visual equality. Public interaction/form delivery still needs separate authorized end-to-end verification. Manual approval boxes are intentionally not pre-checked.

Use the capture report for the **real** pilot alongside `audit-approved-site.cjs`, compare actual proportional layout across the full page (not just its first 540 px), log deviations, fix the first-party design implementation, and repeat capture into a **new** evidence folder to preserve the previous evidence. The same three concept images may not prove every secondary page's appearance: obtain additional real approved page references where required, never invent them.
