# External approved website: folder handoff

**Purpose:** Connect an externally developed **finished site**, built only after client approval of three static prototype images. This is neither a PNG-to-code converter nor evidence that the client really approved; the operator must confirm approval. The original sealed folder remains the portable source of truth. Sealed v2 source evidence is also stored in the private owner-only CMS archive after import.

```text
approved-site/
  handoff.json
  site.json
  prototypes/desktop.png
  prototypes/tablet.png
  prototypes/mobile.png
  client-explanation.md
  implementation-spec.md
  assets/asset-hero.jpg
  assets/asset-hero-mobile.jpg  # optional responsive image variant
  assets/asset-video.mp4        # optional site-owned MP4, up to 16 MiB
```

```json
{
  "format": "manufact-approved-site-handoff-v1",
  "status": "approved",
  "version": "client-approved-v1",
  "files": {
    "site": "site.json",
    "desktop": "prototypes/desktop.png",
    "tablet": "prototypes/tablet.png",
    "mobile": "prototypes/mobile.png",
    "clientExplanation": "client-explanation.md",
    "implementationSpec": "implementation-spec.md"
  }
}
```

The `site.json` is the actual completed site contract (`manufact-ai-site-v1`) using **already registered** CMS component manifests. Image and MP4 media referenced in `site.assets` must exist in folder paths corresponding to the canonical `/assets/...` URL; responsive variants have the same requirement. The code/renderer is not generated by this import. No executable third-party HTML, JS, external URLs or new component definitions are imported.

In authenticated server Studio, the owner chooses **Подключить готовый сайт**, picks the folder in a Chromium-compatible directory picker, and confirms the real client approval. The existing typed validator checks the actual site JSON. The existing authenticated API first creates a nonpublished seed (because createSite forbids unstored images), stores each real image/MP4 into this site's isolated database, issues new immutable IDs, and Save replaces the seed with the fully mapped site manifest. Current page/FAQ/SEO/image editing, Publish and rollback work via the existing CMS path. No network requests to AI providers; no publication without separate user action.

Limitations: image sources are PNG/JPEG/WebP up to 1 MB per source and variant, at most three supported responsive image variants; an optional local MP4 per media asset can be up to 16 MiB and is checked against the same restricted MP4 box structure used by PHP VideoGuard. site.json <=500 KB, prototype image <=8 MB, full handoff <=100 MiB; SVG still needs a separate Studio flow. Client explanation and portable specification are required to be present but qualitative review is human. Errors stop import; after remote creation a recoverable *unpublished* partial seed may remain, never a half-published site. Preserve the original local folder; sealed v2 imports also retain private immutable approved prototypes, source JSON and descriptions in the CMS. Unsupported custom HTML components are a future contract integration task, not automatically 'converted'.

## Individual AI-authored sections (no fixed templates)

**Contract support:** The registered `custom-section@1.0.0` component allows an external AI to deliver an original visual composition in `section.designGraph`, without claiming that one of the fixed demo blocks reproduces its design. The section must contain exactly one `section-note` element with `values: {"content.text":"<internal note>"}`; this field is internal metadata, not the published title. The actual page is rendered from the typed graph and edited through Studio's Design Graph controls. `designGraph` is mandatory for this component in both browser and server validators, so empty or half-built custom sections cannot be saved/published.

The existing Design Graph vocabulary supports containers, headings, text, safe links/buttons, images, icons, separators and controlled video, with independent responsive rules, hover/focus styles and allowlisted motion. The external AI must write these nodes, their responsive styles, actual media IDs and interactions into `site.json`. This is an **individual design**, not unrestricted HTML/CSS/JavaScript import. A client-approved design that needs a behavior beyond the current controlled vocabulary must be explicitly implemented and reviewed as a versioned first-party CMS capability before import. The three static prototype images and full descriptions remain mandatory.

Example section (append to a page's `sections` array; replace the graph nodes with the actual approved design):

## Preflight for a complete external AI handoff

Before opening Studio, run from repository root:

```sh
node stage3/bin/verify-approved-site.cjs /absolute/path/to/approved-site
```

The command validates all existing registered manifests including `custom-section`, graph IDs and allowed styles, cross-section asset references, required three prototype files, descriptions, image MIME/size and responsive variant SHA256. It performs **no writes, network calls, automatic approval or publication**. An affirmative report means structurally compatible, **not** that the actual visual design matches the client's approved prototype. The user still reviews the visuals and explicitly imports/publishes in Studio.

When the owner adds a `custom-section` manually inside Studio, the editor supplies a safe editable starter Design Graph so the UI can open it. This convenience never changes imported `site.json`: direct external site handoffs missing `designGraph` are rejected in browser/PHP. Do not pass the starter graph off as the client's finished design.

## Versioned SHA-256 approval lock (v2)

The earlier `manufact-approved-site-handoff-v1` format remains readable for historical handoffs. For a newly approved client website, seal the finished folder:

```sh
node stage3/bin/seal-approved-site.cjs /absolute/path/to/approved-site client-approved-v1 --confirmed-approved
node stage3/bin/verify-approved-site.cjs /absolute/path/to/approved-site
```

Sealing requires the operator's explicit confirmation of actual client approval. It is **not** proof that a client approved the design. The resulting `manufact-approved-site-handoff-v2` file contains SHA-256 digests for `site.json`, all three prototype images, both text documents, every original image and every responsive variant referenced from the site. Studio verifies the same hashes **before its first server write**. A changed specification, image, mockup or website manifest fails closed. When a client approves a new revision, re-seal deliberately using a new version with `--confirmed-approved --replace`; do not silently edit a sealed package. The integrity lock detects local package modification; it is not a digital signature authenticating the client.

The CLI verifies compatibility with the registered component and Design Graph vocabulary but cannot judge whether final HTML visually matches the three actual mockups. Keep the original versioned handoff separately; the CMS does not store its prototype evidence.

## Resuming a partially uploaded sealed site, including after lost tabs

Before the first image upload to a newly created isolated site, hosted Studio now stores **two immutable owner-only recovery anchors** from the exact SHA-256 sealed v2 folder: original `handoff.json` and `site.json`. The already-existing approval evidence vault verifies the sealed handoff ledger and site ID, without a new database table or secret in the public site. In an interrupted import, this anchor remains explicitly **incomplete** (not an approval-complete record); the full evidence package is completed only after the finished site has been saved.

To continue, sign in as the CMS owner, choose **Подключить готовый сайт** and reselect the **same sealed folder**, even in a new browser tab or after clearing browser session storage. The importer first verifies the local sealed file ledger, current unpublished site's exact untouched initial seed, stored handoff and site.json SHA256 **including their actual server-held bytes**, then displays the approved images and local rendered site. When recovering without a same-tab ticket, the owner must check an explicit recovery acknowledgement tied to this site ID and sealed SHA prefix. Before any new write, Studio rechecks server revision and unpublished status, verifies each existing original and responsive asset's actual byte SHA256, rejects unexpected media and uploads **only missing assets**. It then saves one new unpublished draft revision and idempotently completes the full approval evidence vault. The existing same-tab checkpoint remains a limited fallback for old interrupted v2 seeds where durable anchors could not be fully recorded.

**Fail-closed boundaries:** a different sealed package, foreign approval evidence, modified seed, published site, unexpected/mutated uploaded image, missing anchors without an old same-tab ticket, or legacy v1 cannot be silently adopted. The recovery procedure never overwrites a finished client site, deletes data, or publishes automatically. If the initial Create response is lost before both durable anchors reach the server, cross-tab recovery is intentionally **not guaranteed**. This is recovery of an unfinished seed, **not a fully atomic all-or-nothing multi-file import**; unsuccessful attempts may leave an isolated unpublished partial seed for manual review.

Total portable package still has the existing 100 MB preflight budget; the `manufact-site-backup-v2` JSON archive still has a 64 MB cap and explicitly fails when exceeded. None of these checks establish that any human actually approved the design.


## Real client media quality — 1 MB source and responsive variants

To avoid aggressively downscaling client photography during a genuine site pilot, every **PNG/JPEG/WebP original and individual responsive variant now has a 1,000,000-byte limit** (was 450,000). This is enforced consistently by offline seal/verify, browser pre-import checks, authenticated PHP media upload, Media & Motion workbench, private preview/resume verification and complete backup/restore. The bounded JSON media upload request accepts a base original plus at most three 1 MB variants; their original SHA-256 values and decoded dimensions still must match, and each immutable server-owned media ID is isolated to the site. The 4,096px dimension limit and whitelist remain unchanged. A photo larger than 1 MB should be optimized *before sealing the approved package*; the CMS never silently transforms already approved immutable source files. PHP JSON post sizes must permit at least 6.5 MB for a fully populated request. Large media collections plus 60 possible approved mockups can exceed the **unchanged 64 MB complete-backup cap**: export fails explicitly; do not mistake a failed backup for a complete recovery artifact. Separate individual source files remain downloadable from the private evidence vault. No video, SVG, arbitrary HTML or third-party executable upload is enabled by this change.


### Pre-import capacity checks and immutable output
The offline `verify-approved-site.cjs` result includes `approvedPrototypeBytes` and `sourceAssetBytes`; `audit-approved-site.cjs` records them and the **minimum Base64 footprint** of originals and responsive media before CMS history. The Studio client review displays the byte total and warns if even the minimum image-only footprint approaches the 64 MB all-in-one backup ceiling. This is an estimate, **not a guarantee that backup succeeds**; revisions, submissions, more approved versions and document metadata add size. At export the server independently validates the complete archive and refuses oversize, never discarding approved files. Always preserve the original sealed source folder as an independent off-CMS backup and test a full v2 export/restore with the real site.


## Owner private extended backup bundle (CLI only)

For a site whose **complete** `manufact-site-backup-v2` JSON exceeds the HTTP 64 MB cap, the lead branch now provides a separate bounded private transport, `manufact-site-backup-bundle-v1`. It wraps the exact validated v2 archive in numbered 8 MB binary parts and a SHA-256 manifest, preserving **all** revisions, releases, media, submissions, operator notes and immutable approved source evidence. The extended maximum is **256,000,000 bytes** of full v2 JSON, not unlimited; this implementation assembles the archive in PHP memory and requires adequate operator CLI RAM/disk. It cannot silently remove any source files to fit. Do not expose the bundle directory under a public document root. The existing HTTP backup/restore stays **strictly 64 MB**; v1/v2 compatibility is unchanged.

Run only with a configured, isolated `STAGE3_DSN` and after the explicit approval-evidence schema migration on older databases. Export into a **new absolute directory** under a private writable parent:

```sh
STAGE3_ALLOW_BUNDLE_EXPORT=YES php stage3/server/bin/archive-bundle.php export site-example /private/backups/site-example-20261028
php stage3/server/bin/archive-bundle.php plan /private/backups/site-example-20261028 site-example-recovery
STAGE3_ALLOW_BUNDLE_RESTORE=YES php stage3/server/bin/archive-bundle.php restore /private/backups/site-example-20261028 site-example-recovery
```

The plan/restore reads **all** parts, rejects symlinks/unexpected files/size and SHA mismatches, then applies existing v2 domain/reference/evidence verification. Restore refuses to overwrite a site and uses one database transaction to create a **new unpublished** site. SHA-256 is integrity detection, **not** an authenticated client approval signature or confidentiality mechanism. Store these unencrypted files in private access-controlled storage, make an off-host copy, and validate recovery. If a site exceeds 256 MB, the command **fails explicitly**; further truly streamed recovery must be designed before onboarding it, not bypassed with higher unreviewed limits.

## Safe interactive nodes in individual Design Graphs

Custom Design Graph sections now support `disclosure`, `tabs` and `tab` as typed interactive elements alongside free-form, safely validated layout, typography and media. A disclosure uses native `details/summary` semantics and holds 1–30 nested nodes. A tab group holds 2–8 direct `tab` children; every tab has a short label and at least one nested content node. CSS-only radio selection with keyboard focus and `:has()` panel visibility makes individual tab groups interactive without importing arbitrary JavaScript. These are native radio-group controls, not an ARIA tablist; external designers must assess the intended tab UX, browser support and accessibility.

The browser SDK and PHP renderer both validate the hierarchy; invalid/stranded tabs and executable code are rejected. Studio supports editing nested content, responsive properties, copying, reordering and Undo. Approved customer screenshots and specifications remain the reference, and there is no claim of client visual acceptance from these tests.


### Semantic ordered and unordered Graph lists

A `list` node is an accessible `ul` or `ol`, with `ordered: true|false` and **1–24 immediate `list-item` children**. Each item is an escaped, editable plain-text node with a stable ID; it may be cloned or reordered within its list using the same typed Design Graph edit operations and Undo. List items outside a list, non-item children inside a list, unrecognized attributes and unsafe raw HTML/JS fail validation in browser SDK and PHP. Studio can build a ready-to-edit two-item list, add points within the full Design Graph editor, change numbered/bulleted styling and edit item text. These are per-site custom compositions, not a new template factory.


## Rich individual content, not a site template

The typed \`designGraph\` for each \`custom-section@1.0.0\` can now represent actual per-project content beyond headings and images. The browser SDK, first-party Studio and PHP runtime share the same validation rules; no arbitrary client HTML/CSS/JS or external assets are allowed.

- **\`link\`** is a plain inline text link distinct from a styled \`button\`. Both accept validated relative site paths, \`https://\` URLs, simple \`mailto:user@example.org\` and international \`tel:+48123456789\` actions. Email query headers, \`javascript:\`, \`data:\`, protocol-relative URLs and untrusted schemes are rejected. External HTTPS links get \`rel="noopener noreferrer"\`. Existing on-site link/anchor audits also check \`link\` nodes.
- **\`quote\`** requires plain \`text\` and optionally \`cite\` (attribution, max 160 characters). It renders semantic \`figure > blockquote\` plus optional \`figcaption\` with full escaping; it never fabricates a review/source. It is not a published testimonial until the operator supplies real approved wording.
- **\`table\`** has optional text caption, 2–10 direct \`table-row\` nodes, with exactly 2–6 \`table-cell\` nodes per row and **identical column counts**. The first row renders as \`thead\` and scoped \`th scope="col"\`; subsequent rows are \`tbody/td\`. Tables have a keyboard-focusable horizontally scrollable container on small devices. Every cell has its own stable ID and editable plain text. Studio can add/delete columns atomically across the entire table, add rows, edit each cell, duplicate/reorder valid rows, and Undo before Save. Arbitrary unequal columns or detached cells/rows are refused.
- **\`gallery\`** requires a meaningful nonempty \`text\` accessibility label and 2–12 direct image nodes. Its content consists only of previously uploaded, contract-bound site images with explicit alt text. CSS scroll snapping supports manual swipe, scroll and keyboard-accessible region focus without untrusted scripts, external sliders or automatic play. Images can be added, edited, copied and reordered while retaining their real immutable media bindings.

Authoring example: a \`table\` containing two \`table-row\` objects, each with two \`table-cell\` objects \`{"id":"...","type":"table-cell","text":"...","styles":{}}\`. A \`gallery\` contains regular \`image\` nodes with \`assetId\` and \`alt\`, bound to \`site.assets\`; a \`quote\` is \`{"id":"...","type":"quote","text":"...","cite":"...","styles":{}}\`. Each ID must satisfy the existing graph uniqueness constraints. A real client comparison should use verified source values, not example headings or speculative numbers.

Studio workbench and full Design Graph editor expose authoring and per-device style controls; content-wide find/replace can update visible table cells, captions, gallery labels, quote text and attribution, and internal links remain included in the existing quality review. All changes are still **draft-first**, manually saved and only published by a separate owner action. Source approval image parity remains a human gate; schema compliance is not proof that the authored design matches the approved mockups.


## Site-owned responsive artwork and image actions

The approved-site Design Graph vocabulary now supports **real, independently chosen artwork per breakpoint** without injecting CSS or external URLs. On a content node such as \`container\`, \`heading\`, \`text\`, \`button\`, \`link\`, \`quote\`, \`list\`, \`gallery\` or \`disclosure\`, the optional \`backgroundMedia\` is a *closed* object:

\`\`\`json
{
  "assetId": "asset-hero-desktop",
  "tabletAssetId": "asset-hero-tablet",
  "mobileAssetId": "asset-hero-mobile",
  "size": "cover",
  "positionX": 50,
  "positionY": 40,
  "overlay": {"color": "@foreground", "opacity": 35}
}
\`\`\`

All asset IDs must reference raster JPEG/PNG/WebP images already present in the **same site's uploaded and SHA-256-verified media inventory**. These are standalone approved originals, not the automatic 360/720/1200 responsive derivatives of one image. Desktop \`assetId\` is required; omission of \`tabletAssetId\` inherits desktop and omission of \`mobileAssetId\` inherits the latest tablet/desktop image. Breakpoints remain 900/600 CSS pixels.     {"text":"нового поколения","strong":true,"color":"@accent"}
```json
  ]
}
```

Каждый фрагмент имеет непустой текст, необязательные `strong` и `italic` (boolean), необязательный `color` (шестизначный HEX или существующий токен дизайна). Не поддерживаются HTML, JS, сторонние стили или произвольные ссылки внутри текста. Рендерер выпускает семантические `strong/em`, экранирует символы разметки и сохраняет переносы строк через first-party CSS. В Studio у выбранного `heading/text` доступен встроенный редактор фрагментов в **Дизайн-композиция**, без сторонней библиотеки. Изменение общего `text` сбрасывает `runs`; редактирование самих фрагментов синхронно обновляет plain-text значение. Эти возможности подлежат отдельному визуальному сравнению с настоящими утверждёнными макетами, CI не является клиентским GO.

### Кликабельный фрагмент текста
